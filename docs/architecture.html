한 문단 요약

누가 물어보면 이렇게 답하면 된다.

“blur는 빌드 도구 없는 정적 PWA다. HTML·CSS·JavaScript 파일 몇 개가 GitHub Pages에 올라가 있고, 브라우저가 그걸 받아서 앱처럼 돈다. 서버 코드는 우리가 안 짰다 — Supabase(관리형 PostgreSQL)가 데이터베이스·인증·파일 저장·실시간·서버리스 함수를 다 맡는다. 앱은 브라우저에서 Supabase에 직접 말을 걸고, ‘누가 무엇을 볼 수 있는가’는 전부 데이터베이스 안의 RLS 정책이 막는다. 앱을 뜯어봐도 남의 데이터는 안 나온다.”

핵심 감각 하나. 이 앱에는 “우리 서버”가 없다. 중간에 API 서버를 두지 않고 브라우저 → Postgres로 바로 간다. 그래서 보안 경계가 코드가 아니라 DB 정책에 있다. 프론트엔드에서 조건문을 지운다고 남의 사진이 보이지는 않는다.

“어떤 모델을 썼나”에 대한 답

blur에는 AI 모델이 들어가 있지 않다. 사진 분류도, 추천 알고리즘도, LLM 호출도 없다. 앱을 만드는 데 AI를 썼을 뿐, 돌아가는 앱 안에는 모델이 없다. 이건 약점이 아니라 비용·프라이버시·속도에서 전부 유리한 선택이고, 질문받으면 그대로 답하면 된다.

사진에 걸리는 “필터”도 모델이 아니라 손으로 짠 캔버스 픽셀 연산이다 — grain(입자), glass(유리), halftone(망점), naive(단순화), data(데이터) 5종이 app.js의 artGrain()·artGlass() 같은 함수로 구현돼 있다. 전부 사용자 폰에서 계산된다.

전체 구조 3층

화살표 방향이 곧 “누가 누구를 부르는가”다.

1층 — 사용자의 폰 (브라우저)
index.html 껍데기 · app.js 상태와 화면 · styles.css · backend.js 서버 호출 창구 · sw.js 오프라인 캐시와 푸시 수신
사진 편집(자르기·회전·필터)과 동영상 인코딩도 전부 여기서 일어난다
↓ HTTPS · WebSocket ↑
2층 — Supabase (우리가 관리 안 하는 서버)
Auth 카카오·구글 로그인, JWT 발급 · PostgreSQL 테이블 10개 + RLS 정책 + 트리거 · Storage photos 버킷 · Realtime 변경 스트리밍 · Edge Function notify
↓ Web Push (VAPID) ↓
3층 — 푸시 중계망 (애플·구글)
APNs / FCM 같은 브라우저 벤더의 푸시 서비스. 우리는 여기에 암호화된 메시지를 맡기고, 그쪽이 잠금화면까지 배달한다. 앱이 꺼져 있어도 도착하는 이유
브라우저가 Supabase를 직접 부른다는 게 이 구조의 전부다. 그래서 공개된 anon 키(config.js에 그대로 들어 있다)를 누가 가져가도 문제가 없다 — 그 키는 “로그인 화면에 들어갈 자격”일 뿐이고, 실제 권한은 로그인 후 발급되는 JWT와 DB의 RLS가 정한다.

앱이 켜지는 순서

boot() 함수 한 번에 일어나는 일.

01
Service Worker가 파일을 준다 폰 앱 파일은 네트워크 우선(항상 최신 배포를 받고, 끊기면 캐시로). 반대로 Supabase API 응답은 절대 캐시하지 않는다 — 남의 데이터가 굳어버리면 안 되니까
02
세션 확인 getSession(). 로그인 흔적이 없으면 웰컴 화면, 오프라인이면 전용 오프라인 화면(웰컴으로 튕기지 않는다)
03
OAuth 잔여물 청소 로그인 후 주소창에 붙어 오는 ?code=·#access_token=을 history.replaceState로 지운다
04
데이터 8종을 한꺼번에 서버 loadAll()이 프로필·게시물(+댓글)·친구관계·내 블러해제기록·허브주제·친구추천·메시지·내 연락처해시를 Promise.all로 동시에 받는다. 순차 호출이 아니라 병렬이라 첫 화면이 빠르다
05
서버 행 → 앱 상태로 변환 mapProfile·mapPost가 DB 컬럼명을 앱 내부 이름으로 바꾼다. 내 글은 자동으로 ‘열람됨’ 처리
06
첫 로그인이면 이름·아이디 설정 화면 profiles.setup_done이 false면 setup 화면. 이름은 카카오·구글 프로필에서 미리 채워준다
07
실시간 구독 시작 subscribeRealtime이 4개 테이블을 구독. 변경 신호가 오면 450ms 디바운스 뒤 loadAll을 다시 돌린다. 탭에 돌아올 때(visibilitychange)도 마찬가지
알아둘 설계 습관: 실시간 이벤트가 와도 “바뀐 그 행만” 고쳐 넣지 않고 전체를 다시 받는다. 데이터가 작을 때는 이게 훨씬 안전하다(부분 갱신은 상태 불일치 버그의 온상). 사용자가 수백 명을 넘기면 이 결정을 다시 봐야 한다.

로그인 — 왜 비밀번호가 없나

2026-07-19에 자체 계정을 전부 버리고 소셜 로그인 전용으로 갈아탔다 (migration-09).

01
“카카오로 계속하기” signInWithOAuth({ provider }) → 카카오 동의 화면으로 페이지 자체가 이동한다
02
카카오가 Supabase로, Supabase가 우리 앱으로 돌려보낸다 돌아올 때 URL에 인증 코드가 붙어 오고, Supabase 클라이언트가 그걸 세션(JWT)으로 바꿔 브라우저에 저장한다
03
DB 트리거가 프로필을 자동 생성 서버 auth.users에 행이 생기는 순간 handle_new_user() 트리거가 profiles 행을 만든다. 앱이 따로 요청하지 않는다
04
이름·아이디 설정 아이디는 영문 소문자·숫자 4~16자, 전역 유일(대소문자 무시). 중복 검사는 is_handle_available RPC를 타이핑 중 디바운스로 호출

이 선택으로 사라진 것들

  • 비밀번호 저장·해싱·재설정 메일 — 전부 카카오·구글이 책임진다
  • 복구 코드 시스템 (migration-08에 있던 것을 09에서 제거)
  • 합성 이메일 주소 방식 (@아이디로 로그인하려고 만들었던 편법)

대신 카카오·구글 콘솔 설정에 의존하게 됐다. 리다이렉트 URL 허용 목록이나 동의 항목이 어긋나면 로그인이 통째로 죽는다 — 도메인을 바꾸거나 계정을 옮길 때 반드시 같이 손봐야 하는 지점. 절차는 docs/oauth-setup.md.

얼마나 쌓이나 — 실제 크기 감각

텍스트 행은 사실상 무게가 없다. 댓글 100자면 넉넉잡아 0.3KB, DM도 비슷하다. 사용자 100명이 하루 100개 댓글을 써도 하루 30KB. Supabase 무료 티어 DB 500MB를 텍스트로 채우려면 수십 년이 걸린다.

부담은 전부 사진·동영상이다. 그리고 이건 앱이 올리기 전에 미리 줄여서 보낸다.

사진

긴 변 1080px, JPEG 품질 0.88 — 대략 150~400KB

동영상

최대 5초, 720p(무거운 필터는 540p), 3Mbps, 무음 — 대략 1.5~2MB

하루 상한

한 사람당 게시물 1개 (DB 제약 one_post_per_hub)

100명 × 30일

전원 사진이면 약 0.9GB, 전원 동영상이면 약 5GB

무료 티어

Storage 1GB — 여기가 먼저 찬다. 사진만 써도 3~4개월

“하루 한 장” 제약이 사실은 비용 설계다

UX 컨셉으로 보이는 one_post_per_hub 제약이 스토리지 증가율을 사용자 수에 선형으로 못박는다. 사용자가 폭주해도 하루 저장량은 (사용자 수 × 최대 2MB)를 절대 못 넘는다. 예측 가능한 비용 — 이게 이 제약의 숨은 값어치다.

사진 파일이 실제로 놓이는 자리

photos/                          ← 버킷 (public)
  {user_id}/                     ← 사람마다 자기 폴더
    post-1783429...-a3f9.jpg     ← 게시물 사진
    post-1783512...-b71c.mp4     ← 동영상
    avatar-1783440...-c2d8.jpg   ← 프로필 사진

업로드는 본인 폴더에만 가능하다 — Storage 정책이 경로 첫 칸({user_id})을 로그인한 사람의 ID와 비교한다. 남의 폴더에 못 쓰고 남의 파일을 못 지운다.

알고 있어야 할 트레이드오프: 버킷이 public이다. 즉 사진 URL을 아는 사람은 로그인 없이도 그 이미지를 볼 수 있다. 블러는 화면 효과(CSS)일 뿐 파일 자체는 선명하다. URL이 추측 불가능한 무작위 문자열이라 실질 위험은 낮지만, “유출되면 안 되는 사진”을 담는 서비스로 크려면 비공개 버킷 + 서명 URL로 전환해야 한다. 스키마 주석에도 그렇게 적혀 있다.

브라우저에 남는 것

서버가 아닌 폰에도 조금 남는다 — 로그인 세션(JWT), 배경색 취향, 알림을 마지막으로 본 시각. 사진이나 대화 내용은 로컬에 저장하지 않는다. 초기 MVP는 전부 로컬에 뒀지만 Supabase 연동 때 걷어냈다.

사진 한 장이 올라가는 전 과정

탭에서 DB 행까지. 무거운 일은 전부 폰이 한다.

01
고르기 폰 카메라 또는 앨범. <input type="file"> 하나로 끝 — 네이티브 권한 요청 코드가 필요 없는 게 웹의 이점
02
1차 축소 폰 읽자마자 긴 변 1400px·품질 0.82로 줄인다. 원본 4000px 사진을 메모리에 들고 다니면 편집 화면이 버벅인다. 동영상은 여기서 길이를 검사해 6초 이상이면 즉시 거부
03
편집 폰 비율(고른 사진의 실제 비율이 기본값)·확대·회전·이동·필터 5종. 이 단계는 아직 미리보기일 뿐 — 원본은 그대로다
04
굽기 (bake) 폰 “올리기”를 누르는 순간 캔버스에 실제로 그린다. 사진은 1080px·품질 0.88로 한 장, 동영상은 프레임마다 필터를 칠하며 MediaRecorder로 최대 5초 재인코딩(무음)
05
Storage 업로드 서버 {내ID}/post-{시각}-{무작위6자}.jpg로 올리고 공개 URL을 돌려받는다
06
posts에 행 삽입 서버 사진 URL·캡션·비율·필터·공개범위를 담아 insert. DB가 여기서 두 번 검사한다 — 오늘 이미 올렸으면 거부(one_post_per_hub), 날짜가 오늘이 아니어도 거부
07
친구 화면에 자동 등장 모두 Realtime이 posts INSERT를 흘려보내고, 볼 자격이 있는 사람의 앱만 화면을 갱신한다

실패해도 안 깨지게 만든 자리

  • 아트 필터가 터지면 필터 없는 사진으로 그냥 올라간다 — 게시가 실패하지 않는다
  • 동영상 필터가 중간에 터지면 나머지 프레임만 무필터로 계속 굽는다
  • 캔버스 굽기 자체가 실패하면 편집 전 이미지로 폴백

“사용자가 올리려던 것은 어떻게든 올라간다”는 원칙이 코드에 세 겹으로 들어가 있다.

사람 사이 소통

친구 → 댓글 → DM. 세 개 다 같은 원리로 돈다.

친구 관계 — 두 사람에 한 행

A와 B가 친구면 행이 하나다(두 개가 아니라). 저장할 때 UUID 크기순으로 정렬해서 user_a < user_b로 고정한다. 덕분에 “관계가 이미 있나?”를 확인하는 질의가 항상 단순해지고, 중복 요청이 기본키 제약에 걸려 저절로 막힌다.

status뜻바꾸는 사람
pending요청 보냄, 대기 중보낸 사람이 행을 만든다
accepted친구요청받은 쪽만 수락 가능 (자기 요청 자가수락 차단, migration-07)
blocked차단당사자 누구나. 차단당한 쪽은 행을 지우고 재요청할 수 없다

아이디 검색

직접

@아이디로 정확히 찾는다. 프로필 기본정보는 누구나 조회 가능하도록 열려 있다 — 검색이 성립하려면 필요한 개방이다.

친구의 친구

RPC · friend_suggestions

내 친구의 친구를 서버 함수가 계산해서 추천한다. 겹치는 친구 수도 같이 온다.

연락처 매칭

해시 · 안드로이드 크롬만

전화번호 원본은 서버에 절대 안 간다. 폰에서 번호를 정규화해 SHA-256으로 해싱하고, 해시만 보내 교집합을 받는다. 그마저도 “내가 이미 가진 번호”와만 대조되므로 임의 번호의 가입 여부를 캐낼 수 없다.

댓글과 DM

댓글은 comments(1~100자), DM은 messages에 그냥 행으로 쌓인다. 읽음 처리는 read_at에 시각을 찍는 것뿐이다. DM 본문은 보낸 뒤 수정할 수 없다 — 읽음 처리 정책이 본문 수정까지 열어주던 구멍을 migration-07에서 막았다. 삭제는 보낸 사람만, 그리고 지우면 상대 화면에서도 사라진다.

화면이 실시간으로 바뀌는 이유

내가 댓글을 쓴다
  → comments 테이블에 INSERT
    → Postgres 논리 복제(logical replication)가 변경을 흘린다
      → Supabase Realtime이 RLS를 통과하는 사람에게만 WebSocket으로 전달
        → 상대 앱의 subscribeRealtime 콜백 실행
          → 450ms 디바운스 후 loadAll() → 화면 갱신

여기서도 RLS가 적용된다는 게 핵심이다. 실시간 채널을 구독해도 볼 자격이 없는 행은 애초에 오지 않는다.

인증 설계에서 배울 점

트리거가 함수를 부를 때 “진짜 우리 DB다”를 증명해야 하는데, Supabase 키를 쓰지 않았다. 키 형식이 두 가지(레거시 eyJ... / 신형 sb_secret_...)라 프로젝트마다 무엇이 들어올지 달라 깨지기 쉬웠기 때문. 그래서 우리가 만든 무작위 비밀을 Vault와 함수 시크릿 양쪽에 두고 그것만 믿는다. Authorization 헤더의 anon 키는 플랫폼 관문을 통과하는 용도일 뿐, 인증 근거가 아니다(공개된 값이니까).

이 구조의 유일한 함정

DB·함수·앱 셋의 버전이 맞아야 알림이 나간다. 마이그레이션만 돌리고 함수를 재배포하지 않으면 구버전 함수가 트리거 호출을 무시해서 알림이 조용히 끊긴다. 실제로 한 번 겪었다.

순서는 항상 ① SQL 실행 → ② supabase functions deploy notify → ③ 앱 배포. 그리고 함수 배포는 반드시 원본 폴더에서 — /tmp/blur-app은 정적 파일 클론이라 함수와 무관하다.

iOS에서만 다른 것

  • 홈 화면에 추가(PWA 설치) 후에만 웹 푸시가 동작한다 (iOS 16.4+). 사파리 탭에서는 안 온다
  • iOS는 알림에 “from blur”를 강제로 붙인다 — 제거 불가라 안드로이드 기준으로 문구를 최적화했다

누가 무엇을 보는가 — RLS

blur의 보안은 전부 여기 있다. 이 섹션 하나만 이해해도 절반은 안 것.

RLS(Row Level Security)는 “이 사람이 이 행을 볼 수 있나”를 데이터베이스가 직접 판단하는 기능이다. 앱이 select * from posts를 던져도, 서버는 그 사람이 볼 자격이 있는 행만 돌려준다. 프론트엔드가 뚫려도, 누가 API를 직접 호출해도 결과는 같다.

게시물이 보이는 조건 — 셋 중 하나

보인다 ⟸  ① 내가 쓴 글
      또는 ② 작성자와 내가 accepted 친구
      또는 ③ 글이 '모두 공개'이고 + 작성자 계정이 공개

③의 뒷조건이 중요하다. 계정을 비공개로 바꾸면 이미 올린 ‘모두 공개’ 글까지 즉시 숨는다. 정책이 저장 시점이 아니라 조회 시점에 판단하기 때문 — 소급 적용이 공짜로 따라온다.

테이블읽기쓰기
profiles로그인하면 전부 (검색이 성립하려면 필요)본인 행만

friendships당사자 둘만요청은 본인 명의 pending으로만

이 표에서 읽어야 할 것: 어떤 테이블도 “전부 읽기 + 전부 쓰기”가 아니다. 그리고 앱 코드에 없는 규칙이 DB에는 있다 — 예를 들어 posts에 어제 날짜로 글을 쓰는 건 불가능하다. 앱 화면에 그런 버튼이 없어서가 아니라, 정책이 거부하기 때문이다.

주제 승인제 — 조용한 안전장치

초기에는 클라이언트가 주제를 자동 생성했다. 지금은 운영자가 미리 승인한 주제만 게시된다. 주제가 없는 날은 “오늘의 주제를 준비하고 있어요”가 뜨고 사진 게시가 잠긴다.

이게 중요한 이유: 부적절하거나 이상한 주제가 자동으로 뜰 가능성이 0이 되고, 필요하면 주제를 안 넣는 것만으로 서비스 전체의 게시를 멈출 수 있다. 대신 매주 topics-weekly.sql을 돌려야 한다 — 잊으면 아무도 사진을 못 올린다. 운영상 가장 실수하기 쉬운 지점.

화면이 그려지는 방식

React를 안 쓰는 앱이 어떻게 상태를 화면에 반영하나. 성능 사고가 여기서 났다.

기본 구조

state (커다란 객체 하나)
  → render()  : state를 읽어 HTML 문자열을 만든다
    → patchPhone() : 화면을 조각으로 나눠 비교
      → 조각의 HTML이 지난번과 같으면 그 노드는 건드리지 않는다

조각은 주 화면·탭바·오버레이·배너·작업중 표시·토스트로 나뉜다. 상태가 바뀌면 update()를 부르고, 그게 render()를 호출한다. 흐름은 항상 한 방향이다.

왜 이렇게 됐나 — 실제 사고 기록

v47~v48

버벅임 · 자판 떨림

원래 render()가 매번 app.innerHTML을 통째로 갈아엎었다. 안 바뀐 사진·동영상까지 전부 새로 만들어져 깜빡임·스크롤 튐·backdrop-filter 재계산이 일어났다. 계측 결과 자판 1회당 스타일·레이아웃 계산이 46회 → 18회로 줄었다.

허브 날짜 — 하루가 바뀌는 시각

blur의 하루는 자정이 아니라 한국시간 오전 6시에 바뀐다. 새벽 3시에 올린 사진은 전날 것이다. 앱과 DB가 이 규칙을 따로 구현하고 있어서(hubDateToday()와 hub_today()) 한쪽만 고치면 어긋난다 — 실제로 예전에 앱은 6시, 정책은 UTC 자정이라 매일 오전 6~9시에 게시가 거부되던 버그가 있었다(migration-07에서 수정).

통계의 한계 — 알고 쓸 것

stats.sh의 “활동 사용자”는 글·댓글·블러열람 중 하나라도 한 사람이다. blur는 로그인·세션 기록을 저장하지 않으므로 앱만 열고 아무것도 안 한 사람은 안 잡힌다. 순수 접속까지 세려면 profiles.last_seen 같은 컬럼을 새로 만들어야 한다.

사진이 공개 URL

보안

URL을 아는 사람은 로그인 없이 이미지를 본다. 무작위 파일명이라 실질 위험은 낮지만, 민감한 사진을 다루려면 비공개 버킷 + 서명 URL로 전환해야 한다.

매번 전체를 다시 받는다

확장성

모든 프로필·모든 게시물을 통째로 받아 앱에서 거른다. 수백 명까지는 문제없지만 그 이상에서는 페이지네이션·증분 갱신이 필요하다. 먼저 깨질 자리는 여기다.

Storage 1GB

비용

무료 티어에서 가장 먼저 차는 곳. 사진만 써도 100명 기준 3~4개월. 다음 단계는 유료 전환 또는 오래된 사진의 자동 정리 정책.

운영자 수동 작업

운영

주간 주제 입력, 신고 확인, 밴 처리가 전부 손이다. 사용자가 늘면 주제 자동화(승인 큐)와 신고 대시보드가 필요해진다.

연락처 찾기가 안드로이드만

플랫폼

Contact Picker API가 안드로이드 크롬 전용. iOS는 내 번호 직접 입력만 가능. 완전 동작은 네이티브 앱(Expo) 재구현 뒤에나.

계정에 묶인 도메인

지뢰

GitHub Pages URL이 계정명에 묶여 있어 계정을 옮기면 베타 사용자 링크가 깨지고 OAuth 리다이렉트 설정도 같이 죽는다. 재개한다면 커스텀 도메인부터.
