## 🔴 먼저 알아야 할 blur 특유의 심사 리스크 3가지

App Store 심사(App Review Guidelines)에서 blur 같은 **UGC 사진 SNS + 소셜 로그인** 앱이 특히 걸리는 지점.

### 1. Guideline 4.8 — Sign in with Apple 필요
카카오·구글 같은 **제3자 소셜 로그인을 제공하면**, 그에 준하는 프라이버시 보호 로그인(= **Sign in with Apple**)을 함께 제공해야 함.
- 현재 blur는 카카오/구글 **전용** → **Sign in with Apple 추가가 사실상 필수**.
- Supabase는 Apple provider 지원 → Expo 재구현 때 `signInWithApple` 추가 + Apple Developer에서 Service ID/Key 설정.
- ⚠️ 이건 자료가 아니라 **개발 작업** → 로드맵 Phase 1에 포함.

### 2. Guideline 1.2 — UGC 앱 안전장치 (5종 전부 필요)
사용자가 사진·글을 올리는 앱은 다음을 **모두** 갖춰야 함:
- [x] 신고 기능 (reports 테이블·4경로 구현됨)
- [x] 차단 기능 (block 구현됨)
- [x] 게시된 EULA/약관 (terms.html)
- [x] 이용약관 동의 절차 (가입 문구)
- [x] **부적절 콘텐츠 필터링 + 24시간 내 신고 처리 약속** — `docs/moderation-plan.md`에 작성 완료(심사노트 KO/EN 포함)
→ **1.2는 전부 충족.** 심사 때 moderation-plan.md 요약을 심사노트에 붙이면 됨.

### 3. Guideline 2.1 — 로그인 전용 앱의 심사용 데모 계정
로그인해야 앱을 볼 수 있는데 blur는 **OAuth 전용**이라 Apple 심사자가 들어올 방법이 없음.
- 대응 A(간단): App Review 정보에 **작동하는 구글 테스트 계정** 이메일/비번 제공 (전용 지메일 1개 생성 권장).
- 대응 B: 심사용 데모 로그인 경로(고정 계정) 임시 추가.
- → Phase 2에서 결정. **전용 구글 계정 생성이 가장 무난.**

## ✅ Phase 1 — 바이너리 만들기 : **Swift / SwiftUI 전면 재구현으로 확정 (2026-08-04)**

PWA는 스토어에 못 올린다. 갈림길은 딱 하나였다 — **지금 웹 코드 7,100줄을 살릴 것인가.**

```
살린다 → Capacitor            ❌ 탈락 (2026-08-04, 김: "기왕 제대로 하고 싶다")
버린다 → 재구현. 스택 선택:
         ├─ Expo (React Native)   ⏸️ 후보로만 남김 (아래 "되돌아갈 조건" 참조)
         └─ Swift / SwiftUI       ✅ 채택
```

### 세 길이 정확히 뭔가
- **Capacitor** = 주소창 없는 사파리 창(WKWebView) 하나짜리 앱. 그 안에서 지금의 `index.html`+`app.js`+`styles.css`가 **한 글자도 안 바뀌고** 실행된다. 화면을 그리는 건 여전히 웹 엔진 — 즉 **웹의 한계도 그대로 따라온다.**
- **Expo(React Native)** = 로직 JS는 Hermes 엔진에서 돌고, 화면은 **진짜 iOS 부품**으로 그린다. HTML도 CSS도 없다(`<button class>` → `<Pressable style>`).
- **Swift / SwiftUI** = 전부 네이티브. JS 엔진도 브리지도 웹 엔진도 없다.

### 비용 비교 (현재 코드 = app.js 3,937줄 + styles.css 2,640줄 + backend.js 417줄 ≈ 7,100줄, 화면 18개 / 사용자 동작 90개)

| | Capacitor ❌ | Expo ⏸️ | **Swift ✅** |
|---|---|---|---|
| 재작성 분량 | 0줄 | ~6,700줄 (`backend.js`는 재사용) | **7,100줄 전부** |
| 현실적 기간(혼자) | 1~2주 | 1.5~3개월 | **4~6주** (풀타임·범위 축소 기준, 아래 계획) |
| 언어 | 지금 그대로 | 지금 그대로(JS) | **Swift 새로 배움** |
| 금전 비용 | $99/년(Apple) 외 0원 | 좌동 | 좌동 |
| 4.2 리젝 위험 | **있음** | 거의 없음 | 없음 |
| 배포 루프 | 재빌드+심사 (Capgo 등 OTA 도구로 완화 가능) | **EAS Update = 즉시**, 현재 루프 유지 | **없음 — 모든 수정이 심사 1~2일** |
| `test/run.sh` 59개 검사 | 그대로 유효 | 폐기 → Maestro 등으로 재작성 | 폐기 → XCTest/XCUITest로 재작성 |
| v47~v54 체감 튜닝 | 살아남음(같은 WebKit) | 버려짐 — 대신 **문제 자체가 사라짐** | 좌동 |
| 완성도 천장 | 웹 수준 | 거의 네이티브 | **제한 없음** |
| 남는 실력 | 적음 | RN(JS 자산 확장) | **iOS 개발 실력** |

> 💡 **재구현을 고르는 진짜 이유**: v47~v54에서 잡은 버그 — 자판 떨림, 뷰포트 높이 어긋남, 번쩍임, 가로 슬라이드 직접 구현 — 은 **전부 웹으로 네이티브를 흉내내다 생긴 것**이다. Swift/RN에선 키보드 회피·화면 전환·스크롤이 OS 기본 동작이라 애초에 안 생긴다. Capacitor는 같은 WKWebView라 이 부류를 그대로 들고 간다.

> ⚠️ **시간의 정체는 "AI가 코드 쓰는 시간"이 아니다.** 초안은 하루이틀이면 나온다. 오래 걸리는 건 ① 실기기에서 화면 하나씩 손으로 확인 ② 푸시·OAuth·권한처럼 실기기+실인증서 없이는 검증 안 되는 것 ③ 심사 왕복. **Swift는 여기에 "OTA가 없다"가 더해진다 — 오타 하나도 심사 왕복.**

### ⏸️ Expo로 되돌아갈 조건
3주차(아래 계획)가 끝나는 시점에 화면 18개 중 절반이 실기기에서 안 돌면, 6주 안에 못 낸다는 신호다. 그때 Expo 재검토 — 단 그 시점엔 이미 Swift에 3주를 썼으므로 **되돌리는 비용이 크다.** 판단은 김이.

### 어느 쪽을 골라도 반드시 해야 하는 개발 4가지
- [ ] **Sign in with Apple** (Guideline 4.8 — 구글 로그인을 제공하면 강제)
- [ ] **푸시를 APNs로 전환** — 현재 웹푸시(VAPID)는 네이티브에서 안 옴. `notify` Edge Function에 분기 필요
- [ ] 구글 OAuth **딥링크 리다이렉트**
- [ ] 카메라·앨범 네이티브 연결
- [ ] ~~연락처 네이티브 권한~~ → **v1에서 제외 확정** (아래 범위 참조)

> 🚨 **오독 방지 — "필터"는 아트 필터 5종만 말한다.**
> **사진을 가리는 블러는 필터가 아니라 이 앱의 핵심 기능이다. 절대 빼지 않는다.**
> (`ART_FILTERS = ["grain","glass","halftone","naive","data"]` ← 이 5개만 제거 대상)

> 📎 기존 사진 처리: 아트 필터는 업로드 시 이미지에 **구워서 저장**되므로 이미 올라간 사진은 그대로 보인다. 다만 표시용 톤 보정(`toneFilter` — warm/vivid/calm/mono)이 남아 있는 옛 사진은 Swift에서 원본 톤으로 보인다. 무시 가능한 수준.
